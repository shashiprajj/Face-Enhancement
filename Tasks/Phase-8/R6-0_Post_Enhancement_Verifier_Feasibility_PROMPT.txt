R6-0 — POST-ENHANCEMENT SAFETY VERIFIER FEASIBILITY STUDY

OBJECTIVE
Determine whether a post-enhancement verifier can reliably decide whether a NAFNet-generated enhancement candidate is safe to return, or whether the candidate should be discarded and the untouched original returned.

TARGET ARCHITECTURE

INPUT
  -> basic technical checks
  -> NAFNet enhancement candidate
  -> POST-ENHANCEMENT SAFETY VERIFIER
       PASS -> enhanced candidate
       FAIL -> original

The original image must always remain available as the safe fallback.

THIS IS A FEASIBILITY STUDY ONLY.

DO NOT:
- modify production behavior
- tune blur thresholds
- modify R5-6, R5-8, or R5-10 behavior
- change the NAFNet model
- introduce another enhancement model
- modify API/UI behavior
- integrate Feature-Match
- search for new datasets/models
- turn this into another threshold-tuning exercise

The only question is:
Can we reliably detect unsafe/bad NAFNet outputs AFTER enhancement?

If the answer is no, stop. Do not manufacture a verifier just to obtain GREEN.

============================================================
2. R6-0 SCOPE
============================================================

Evaluate a post-enhancement verifier containing these signal families:

1. Geometry / face integrity
2. Photometric / colour integrity
3. Texture / frequency integrity
4. Localized difference analysis
5. Identity consistency

Do not implement the final production TRY -> VERIFY -> COMMIT pipeline in this task.

============================================================
3. EVALUATION CORPUS
============================================================

Use EXISTING R5 evidence. Do not create a new synthetic benchmark from scratch.

Create an explicit corpus with:

A. GOOD
Known acceptable NAFNet outputs from R5 evaluations, including representative:
- strong blur
- moderate blur
- noise
- grayscale
- low contrast
- different face sizes
- archive data
- real images where available

B. BAD / KNOWN FAILURE
Include all recoverable known failures, including:
- R5-7 rainbow/dotted outputs
- R5-8 known artifact cases
- R5-10 image_84257
- R5-10 real img118
- previously identified destructive NAFNet outputs
- other explicitly labelled failures in R5 reports

C. BORDERLINE / AMBIGUOUS
Include examples such as:
- moderate blur
- strong blur
- motion blur
- noisy faces
- grayscale
- low contrast
- JPEG degradation
- small faces
- printed/halftone images
- suspicious but non-destructive changes

Report exact counts for all three categories.
Do not silently classify uncertain examples.

============================================================
4. SIGNALS TO EVALUATE
============================================================

4.1 GEOMETRIC INTEGRITY

Measure where possible:
- face bounding-box change
- landmark displacement
- face proportions
- landmark validity
- face detector confidence before/after
- obvious geometric deformation

Goal: detect face warping or structural damage.

4.2 PHOTOMETRIC / COLOUR INTEGRITY

Measure:
- RGB/channel deltas
- luminance delta
- global chroma delta
- local chroma delta
- grayscale preservation
- extreme pixel/channel changes
- localized colour changes

Goal: detect failures such as the img118 colour-mottling case.

4.3 TEXTURE / FREQUENCY INTEGRITY

Measure relevant signals for:
- high-frequency energy
- high-frequency chroma energy
- edge-energy change
- ringing/halos
- periodic texture
- grid/dot patterns
- localized frequency spikes
- unnatural texture creation

Goal: detect rainbow artifacts, dots, grids, ringing, artificial texture, and high-frequency explosions.

4.4 LOCALIZED DIFFERENCE ANALYSIS

REQUIRED.

For every candidate analyze:
    abs(enhanced - original)

Do not rely only on one global difference score.

Measure appropriate signals such as:
- changed-pixel percentage
- largest connected changed region
- concentration of changes
- local chroma concentration
- local high-frequency concentration
- spatial distribution of changes

Goal:
distinguish distributed/natural deblurring from small localized artificial patches.

4.5 IDENTITY CONSISTENCY

Calculate where available:
- SFace similarity: original -> enhanced
- dlib similarity: original -> enhanced
- embedding movement/delta

IMPORTANT:
Identity similarity is a SAFETY signal, not proof that enhancement is good.

Do not claim:
"SFace passed, therefore the enhancement is safe."

Use identity movement as a conservative reject signal for substantial identity drift.

============================================================
5. INDIVIDUAL SIGNAL ANALYSIS
============================================================

For each signal:
1. Calculate its distribution on GOOD examples.
2. Calculate its distribution on BAD examples.
3. Calculate its distribution on BORDERLINE examples.
4. Determine whether it provides meaningful separation.
5. Identify known failure cases it misses.
6. Identify GOOD cases it would incorrectly reject.

Produce a table similar to:

Signal | GOOD | BAD | BORDERLINE | Separation | Known misses

Do not hide overlapping distributions.

============================================================
6. COMBINATION ANALYSIS
============================================================

Evaluate whether combinations provide better separation.

Potential families:
- photometric + local artifact
- texture + local artifact
- geometry + identity
- photometric + texture + local artifact
- all safety families

Do not blindly invent arbitrary thresholds.

If thresholds are required for research:
- derive them only from the documented corpus
- document selection method
- keep them research-only
- do not modify production configuration

============================================================
7. FALSE ACCEPT / FALSE REJECT
============================================================

Measure:

FALSE ACCEPT:
BAD candidate -> verifier PASS

This is the dangerous failure.

FALSE REJECT:
GOOD candidate -> verifier FAIL

This sacrifices enhancement benefit but is safer.

The verifier should be conservative.

Report:
- false-accept count/rate
- false-reject count/rate
- exact examples involved
- why the verifier failed

============================================================
11. FINAL VERDICT
============================================================

GREEN — VERIFIER FEASIBLE
Use only if evidence shows the verifier can meaningfully detect known unsafe/bad outputs while retaining a useful amount of good enhancement.
Then recommend R6-1:
    TRY -> VERIFY -> COMMIT

YELLOW — PROMISING BUT INSUFFICIENT
Some signals work, but separation is not reliable enough for safe implementation.
Do NOT implement production routing.
Document exactly what evidence is missing.

RED — NOT FEASIBLE WITH CURRENT EVIDENCE
Available signals cannot reliably distinguish safe from unsafe outputs.
Do NOT manufacture a safety verifier.
Recommend stopping and reassessing architecture/data.
