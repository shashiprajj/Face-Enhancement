R5-10 — NAFNet BLUR-ELIGIBILITY RECALIBRATION
MODERATE-BLUR ROUTING + FULL SAFETY VERIFICATION

Repository: WelOrbit Face Enhancement Service (FES)
Current UI: R5-9 comparison page
Current safe/default profile: R5-6
Current experimental profile: R5-8
R5-8 status: RED; candidate remains research-only
Objective: determine whether the NAFNet input blur gate is unnecessarily restrictive for moderately blurred but still recognizable faces, and, if DEV evidence supports it, widen the eligibility boundary in the smallest defensible way and verify the result end-to-end.

============================================================
1. WHY THIS TASK EXISTS
============================================================

The current UI demonstrated an important real-world problem:

- Some very strongly blurred faces are admitted to NAFNet.
- Some moderately/mildly blurred faces that visibly could benefit are rejected with:
  NAFNET_REJECT_MILD_BLUR / NOT_BLUR.
- Forced A4/SwinIR-L visually improves at least one moderate-blur example, proving that the example is genuinely degraded, but A4 is not the preferred identity model.
- NAFNet has shown substantially stronger identity-similarity benefit than A4 in the controlled archive evaluation.
- Therefore, before abandoning NAFNet, we need to determine whether its blur eligibility threshold is simply too conservative.

The task is NOT:
"Lower the threshold until the owner's image gets enhanced."

The task is:
"Use DEV evidence to determine whether the NAFNet eligibility boundary can defensibly include moderate blur, then freeze it and independently validate it."

The current NAFNet model remains NAFNet-GoPro width64.
Do not replace or retrain the model.

============================================================
2. CRITICAL SCIENTIFIC RULE
============================================================

Do NOT use the owner's real images, archive TEST, ztest, or the 200-real-photo safety set to choose the new threshold.

Threshold selection/calibration MUST happen on DEV data only.

After the candidate threshold is frozen, all TEST/ztest/real-photo evaluations are strictly read-only evaluation.

Do not tune after seeing TEST results.

If the DEV evidence cannot justify a wider boundary, do not widen it.

============================================================
5. CURRENT BLUR GATE
============================================================

The current route uses lapd1_c.

Current known boundaries:

- lapd1_c <= 0.002617: strong low-noise blur -> eligible
- 0.002617 < lapd1_c < 0.005579: mild blur -> rejected
- lapd1_c >= 0.005579: clean/not-blur zone

These are the existing R5 route values.

Do not simply replace 0.002617 with an arbitrary larger number.

The task is to determine the defensible candidate boundary from DEV evidence.

============================================================
18. SUCCESS CRITERIA
============================================================

GREEN requires ALL of:

1. DEV evidence supports the wider blur boundary.
2. The candidate materially increases useful NAFNet coverage.
3. Newly admitted moderate-blur inputs show positive/defensible identity benefit on DEV.
4. Harm does not increase beyond an explicitly justified safety limit.
5. Clean/near-clean inputs remain protected.
6. Other safety gates remain unchanged.
7. Artifact guards remain unchanged.
8. ztest remains contained.
9. 200-real-photo safety does not materially regress.
10. No service failures/restarts/OOM/timeouts attributable to the change.
11. Regression tests pass.
12. Manual UI examples confirm the candidate actually attempts moderate-blur images.
13. No threshold tuning occurred after TEST.

YELLOW:
- Candidate is safe but benefit is weak/inconsistent.
- Or evidence is insufficient to justify production routing.
- Keep as research-only and do not promote.

RED:
- Newly admitted moderate/mild blur produces unacceptable identity harm.
- Artifact leakage increases materially.
- ztest containment regresses.
- real-photo safety regresses.
- clean images become eligible unexpectedly.
- service stability regresses.
- no defensible DEV threshold can be found.

If RED:
- do not keep lowering thresholds
- restore/retain the previous profile
- preserve R5-10 evidence
- stop threshold experimentation
- decide whether NAFNet is still worth Feature-Match testing using the safest available experimental profile

============================================================
19. IMPORTANT STOP CONDITION
============================================================

This task is NOT permission to continuously widen NAFNet eligibility.

Try to find ONE defensible blur boundary.

If the evidence shows:
- strong blur works,
- moderate blur works,
- mild blur does not,

then stop at moderate.

If moderate blur is not safe, stop at the existing boundary.

If no threshold provides a safe and useful operating range, report that conclusion.

Do NOT create R5-10A/R5-10B/R5-10C just by moving the threshold repeatedly.
